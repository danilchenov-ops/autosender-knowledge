## Цель

Снизить стоимость **оплаченного заказа** и нарастить прибыль. Всё остальное —
CTR, цена клика, охват, число заявок — оценивается только через влияние на этот
показатель.

- Бизнес: привоз авто под заказ из Японии, Кореи, Китая. Средний чек ~2 млн ₽.
- **Валовая прибыль с оплаченного заказа — 100 000 ₽** (вводная Тимофея, 18.08.2026).
- Главная метрика: цель «CRM: Заказ оплачен+» (255698794).
- Целевой CPA, названный Тимофеем 20.08.2026: **~25 000 ₽**.
- Порог убыточности: **100 000 ₽** (вся маржа уходит в рекламу).
- **Цикл сделки 30–90 дней.** Свежие периоды и молодые кампании систематически
  занижены по оплатам — судить по ним нельзя.

### Методические находки (записаны в `claude`-проект, журнал ошибок)

- Товарные кампании «ТК …» **не отдаются** через `campaigns.get` ни при каком
  наборе `Types`/`States` — проверено повторно. Читать только через Reports
  и Метрику; недельные лимиты, корректировки и фиды видны лишь в интерфейсе.
- В фильтрах Reports API Директа деньги задаются **в микроединицах**:
  `Cost GREATER_THAN 5000000000` = 5 000 ₽. Значение `4000` означает 0,004 ₽,
  то есть «всё».
- `SEARCH_QUERY_PERFORMANCE_REPORT` не агрегирует и не сортируется по расходу —
  отдаёт строки в алфавитном порядке и обрезает по `limit`. Считать кластеры
  надо через Метрику, namespace `ym:ad:`, с `filters` и без измерений.
- `metrika_api` обрезает ответ на 200 000 символах.
- Базис НДС перепроверен на «ТК Япония НОВАЯ»: 367 330,51 / 301 090,49 = ровно 1,22.

## Принятые решения

Продублированы в `decisions.md`.

- **Все суммы в рекламных расчётах приводить с НДС.** Директ отдаёт расход
  с НДС 22 %, Метрика — без. Расхождение 22 % ломает любой вывод о CPA.
  Коэффициент проверен на реальной кампании, не взят из документации.
- **Кластеры запросов считать фильтрами по всему кластеру, а не по топ-N строк.**
  84 200 фраз, топ-880 покрывают 23 % расхода. Отвергнут разбор по выгрузке
  топа — он давал ложную картину «кругом мусор».
- **Минус-слова этому аккаунту не нужны.** Весь нецелевой кластер — 1 967 ₽/мес,
  0,07 % бюджета. Стандартная рекомендация из чек-листа не применима;
  время на списки минус-слов не тратим.
- **Информационные запросы про калькулятор и растаможку не резать, а
  масштабировать.** Кластер даёт оплату за 13 831 ₽ — вдвое дешевле цели,
  страница калькулятора конвертит в 18 раз выше средней. Отвергнута
  интуитивная рекомендация «минусовать инфо-запросы».
- **Ставить корректировку +30 % на десктоп, а не резать мобильные.**
  Не сокращает объём. Отвергнут вариант «мобильные −25 %»: при 66 % бюджета
  на мобильных это обвал трафика ради недоказанной экономии.
- **«Япония-5» и «Япония-6» — срезать бюджет вдвое, не выключать.**
  Обратимость важнее скорости, кампаниям 26 дней при цикле сделки 30–90.
  Отвергнуто выключение (правило проекта о лаге) и отвергнуто «оставить как есть»
  (цена заявки в 2,5 раза хуже, это от лага не зависит).
- **Временные корректировки не ставить.** Часовой пояс счётчика — Владивосток,
  аудитория от Калининграда до Камчатки. Разброс индекса 1,61 / 0,71 объясняется
  географией не хуже, чем часом. Уверенность 50 % — недостаточно для решения.
- **Порог решения — маржа 100 000 ₽, а не «хуже среднего».** Сегменты между
  средним и порогом корректируем, не отключаем.

## Технические находки по API (дополнение к списку выше)

- **Эндпоинт отчётов для JSON — `/json/v5/reports`.** На `/v5/reports` (без `/json`)
  стоит XML-обработчик: любое JSON-тело получает голое «8000 Некорректный запрос»
  с пустым `errorDetail` (в заголовке ответа `cmd:direct.xml-api/unknown`).
  Полдня отладки. На правильном адресе ошибки приходят с деталями.
- В `params` отчёта **`IncludeVAT` обязателен**.
- Поля `Conversions` / `CostPerConversion` / `ConversionRate` требуют параметра
  `Goals` (опционально `AttributionModels`, напр. `LSC`), иначе ошибка 8000.
- `ReportName` должен быть уникальным — в сервере генерится uuid.
- Метрика: **`ym:ad:goal<id>costPerConversion` не существует** (ошибка 4002),
  CPA считается делением `RUBAdCost` на достижения цели.
  `ym:ad:deviceCategory` тоже нет — устройства с расходом только через Reports Директа.
- **Создание классических текстовых объявлений через API закрыто** (предупреждение
  10251): всё добавляется как комбинаторные баннеры, `Title2` может склеиться
  с `Title` (10253) или отпасть по длине (10254).
- `bidmodifiers.add`: демографические корректировки передаются массивом
  `DemographicsAdjustments`, не объектом.
- `campaigns.add` не принимает `NegativeKeywords` внутри `TextCampaign` —
  только на верхнем уровне кампании.
- Новые кампании создаются в статусе `DRAFT`; `campaigns.suspend` их не берёт
  («кампания является черновиком»), что удобно: черновик не может тратить деньги.
- Директ склеивает фразы, различающиеся только предлогом
  («купить авто в китае» = «купить авто из китая»).
- **Автотаргетинг на поиске отключить нельзя** (обязателен с 2024). Минимальная
  конфигурация: категория «Целевые запросы» + один тип упоминания брендов.
  В тесте выбрано «без упоминания брендов», в брендовой — «с упоминанием вашего бренда».
- **Запрета площадок на уровне аккаунта в Директе нет** — только на уровне кампаний;
  массово удобнее через отчёт «По площадкам» → галочки → «Запретить показы».
  Поисковые проекты Яндекса запретить нельзя.

# Поправка от 21.08.2026 — пункт 11 плана аудита основан на неверном прочтении API

### 15.09 — Тимофей: «не хочу поднимать стоимость цели, давай пропорцию 1:12,7 на произвольных числах»
Ответ по механике: в режиме «максимум конверсий по ценности» с фиксированным недельным бюджетом стратегии
важны **относительные** веса целей, абсолютные суммы не влияют на объём расхода (бюджет — жёсткий лимит).

лимит недельного бюджета не позволяет стратегии тратить больше; меняются только приоритеты внутри лимита.

критичны — придётся переделывать; (3) риск, что через месяц человек или второй агент примет 12 700 за
реальную маржу. Рекомендация: пропорцию задавать **в самих кампаниях**, Метрику не трогать; сначала
закрыть вопрос 49 (где у ТК реально заданы ценности) — до этого правка может быть адресована не туда.

### 15.09 — Челлендж Тимофея: «звонок точно конвертится хуже формы?» — проверка по Метрике
Сегменты посетителей счётчика 56331115, 01.07–13.09, атрибуция CROSS_DEVICE_LAST_SIGNIFICANT:
| Сегмент | Пользователей | → CRM-лид (255698793) | → договор (255698794) | Конверсия в договор |
| Достигли цели «Звонок» (326268791) | 362 | 22 (6,1 %) | **0** | 0 % |
| Достигли «Подобрать автомобиль+» (63078325) | 3 398 | 3 519 (104 %) | 67 | **2,0 %** |

**Честный ответ: нет, утверждать «звонок конвертится хуже» нельзя — это артефакт трекинга, не бизнес-факт.**
Цель 255698794 приходит из CRM офлайн-конверсией по `ym_client_id`, а у звонковых лидов в CRM client_id
пустой (проверено 08.09: 740 лидов «Билайн АТС» с июня, у всех ym_client_id = NULL). Значит покупка
звонившего физически не может засчитаться на эту цель. Ноль договоров у 362 звонивших — следствие разрыва
связки, а не качества звонков. Ранее по CRM конверсия в покупку: форма 4,3 %, звонки АТС 4,2 % — паритет.

**Но как СИГНАЛ ДЛЯ АЛГОРИТМА цель «Звонок» слабая, и это отдельный факт:** из 362 звонивших лишь 22 (6 %)
доходят до CRM-лида, тогда как у формы это 100 %+. То есть 94 % фиксируемых коллтрекингом звонков не
превращаются в лид — справочные, недозвоны, повторные обращения. Учить стратегию на таком событии значит
платить за звонки без подтверждённого продолжения.

**Поправка к развесовке: «Звонок» 500 → 400 без НДС** (на уровень заявки формы, ниже CRM-лида). Обоснование —
не «звонки хуже», а «результат звонка не измеряется». Влияние на запас ничтожно: у Я-2 21 звонок из 646
событий, допустимая средняя 652 → 649 ₽ против факта 650. Развесовка остаётся нейтральной.
**Что починить, чтобы поднять цену звонка обоснованно:** передавать `ym_client_id` в лид при звонке
(коллтрекинг → Битрикс). Через месяц будет честная конверсия звонка в договор — тогда пересмотреть.
Внесено в open-questions как продолжение вопроса о связке звонков.
