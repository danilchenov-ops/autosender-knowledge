# zvonki-transkribaciya

Перенос контекста чата «Система анализа звонков и продаж» (проект «Виртуальный РОП»),
20.08.2026. Факты сверены с сервером, не по памяти переписки.

## Цель

Превратить телефонные разговоры отдела продаж в измеримые данные и на их основе
находить, где теряются деньги.

Три слоя задач:

1. **Не терять оплаченное** — заявки, по которым не позвонили или позвонили поздно.
2. **Довести до конца** — договорённости и обещания, прозвучавшие в разговоре.
3. **Улучшить сам разговор** — скрипт продаж, собранный из выигранных сделок.

Результат измеряется в: доле лидов без единого звонка, медиане времени до первого
касания, среднем числе касаний на лид, доле выполненных обещаний, конверсии.

Наблюдаемые значения на старте (90 дней, август 2026): лидов без звонка 28,6%,
медиана первого касания 7–18 часов по разным менеджерам, среднее число касаний 1,3–1,9,
конверсия базы с рабочими номерами 1,03%.

## Сделано

Всё работает на 5.35.99.93 в `/opt/ropbot`, Docker Compose. Проверено 20.08.2026 09:28 МСК.

### Сбор данных

- **Источник — Битрикс24**, не API Билайна напрямую. Телефония Билайна подключена
  к порталу как REST-приложение, `CALL_RECORD_URL` ведёт на `cloudpbx.beeline.ru`.
- `ropbot-collector-1` опрашивает `voximplant.statistic.get` каждые 5 минут
  (`POLL_INTERVAL=300`), бэкфилл звонков 90 дней (`BACKFILL_DAYS=90`), CRM целиком
  (`CRM_SINCE_DAYS=3650`).
- Собрано: **25 991 звонок, 104 702 лида**, вся история статусов, сделки, дела.
- Нагрузка на Битрикс ~30 запросов в сутки при лимите 172 800 — событийные вебхуки
  не понадобились.

### Расшифровка

- `ropbot-asr-1` и `ropbot-asr-2`, faster-whisper **`large-v3-turbo`**, int8,
  `beam_size=1`, по 2 потока на воркер, порог `MIN_CALL_SEC=30`.
- **Аудио не хранится**: `KEEP_AUDIO_DAYS=0`, файл удаляется сразу после расшифровки.
- Скачивание: прямая ссылка Билайна, при 404 — копия с Диска Битрикса, иначе `skipped`.
- Расшифровано **1 361**, в очереди 7 979, без записи 6.
- Очередь приоритизирована: `asr_queue.priority` — 10 для звонков по выигранным лидам,
  5 для проигранных с 3+ звонками (контрольная группа), 0 для остального.
  **Группа выигранных доехала полностью: 1 065 расшифровок.**

### Метрики разговоров без модели

Считаются автоматически в `call_metrics`: количество вопросов, темп речи, самый
длинный непрерывный кусок речи (прокси монолога при моно-записи), доля тишины,
самая длинная пауза, названа ли цена, есть ли признак следующего шага, стоп-слова.
Пересчёт по сохранённым сегментам — `recalc.py`, аудио не требуется.

- Ограничения: `LLM_MIN_SEC=90`, `LLM_SINCE_DAYS=21`, `LLM_CONF_MIN=0.6`,

- Разобрано **338 разговоров, найдено 114 договорённостей**, они же лежат в `followups`.
- Стоимость ~0,24 ₽ за разговор.

### Правила счёта, зашитые в базу

Записаны также в проектный документ Claude `claude/analytics-rules.md`.

1. **Мусорные телефоны не считаются.** `phone_kind` (`mobile`/`landline`/`junk`/`none`)
   проставляется триггером на `leads` и `calls`. Таких лидов ~7 500, сделок среди них ноль,
   но 1 300 из них были помечены «Недозвон».
2. **Считать по клиенту (номеру), а не по карточке лида.** За 90 дней 1 268 случаев, когда
   с одного номера за сутки заводится 2+ заявки на 2–4 менеджеров. Рекорд — 6 карточек за
   44 минуты. Из-за счёта по карточке первый отчёт по недозвонам показал 47 «потерянных»
   вместо реальных 15.
3. Разделять вину менеджера и дефект процесса — в отчётах это разные разделы.
4. Не путать следствие с причиной, сравнивать внутри однородных групп.
5. Источник `PARTNER` исключать из сравнений — заводится вручную под готовую покупку.
6. Текущий месяц в выводах не использовать: медиана цикла сделки 8,6 дня, 90-й процентиль 38.

- **62–65% заявок приходят, когда офис закрыт** (клиенты в европейской части, офис во

  0,76% — в полтора раза, не вдвое, и без статистической значимости (12 сделок против 24).
  У звонков на рекламный номер 9025240049 разрыва между окнами нет вообще.
  Вывод: разрыв во многом объясняется составом заявок, а не скоростью.
- Оценка потерь: от 0 до +21 сделки в месяц, реалистично **около +5** (~1,8 млн ₽ выручки).
- 63% лидов получают 0 или 1 звонок. «Недозвон» — 31,9% базы, в 72,7% случаев после ≤2 попыток.
- **383 «недозвона» вообще без исходящего звонка**, 94% у двух менеджеров (М6 Николай 191,

- **Повторное обращение — сильнейший сигнал:** номера с 3–4 заявками конвертируются в 5,31%

- Июль: поток +30%, сделок 47 против 52 в июне. Наращивать рекламу нельзя.
- Кампания `tk_708545020`: 801 лид, 1 сделка. Формы сайта (WEB): 44,6% спама.
- Суммы проставлены в 72 из 1 024 успешных сделок, средний чек по ним 349 тыс. ₽.

## Принятые решения

**Источник данных — Битрикс24, а не API Билайна.** Телефония уже интегрирована, записи и
привязка к лидам приходят готовыми. API Билайна остаётся запасным путём.

**Аудио не хранить вообще.** Записи и так лежат в Битриксе, а расшифровки занимают
~0,25 ГБ в год против ~12 ГБ/мес аудио. Отклонено: буфер в 3 дня — оказался не нужен,
свежие записи перекачиваются.

**Модель распознавания — `large-v3-turbo`.** Сравнение на одном живом звонке: `small`
3,3x, но теряет деловые факты («аукционный лист, 4 балла» → «листочка открытой»);
`medium` 1,3x; `turbo` 1,2x и лучшее качество. При равной скорости выбран turbo.
Отклонено: `medium` (хуже при той же цене), `small` (потеря смысла).

**Модель разбора — `gemini-3.5-flash-lite`.** На 12 разговорах: 5 из 5 договорённостей,
ноль ложных, чистая шкала уверенности. Отклонены: `gpt-5-nano` (пропустил 4 из 5),
`gpt-5-mini` (ложное срабатывание на «Будем на связи»), `gemini-2.5-flash-lite`
(пропуск и ошибка в дате). Разница в цене ~800 ₽/мес признана несущественной.

**Провайдер моделей — ProxyAPI.** Рубли, карта РФ, без документов, все модели одним ключом.
Отклонено: GigaChat — freemium запрещён для коммерческого использования, платный пакет
для юрлица требовал договора.

**Telegram через SSH-туннель до заграничного релея.** Отклонено: Битрикс-чат (проще, но
менеджеры не в нём), MAX (не изучен), прокси только для Telegram (менее предсказуемо).

**Считать по клиенту, а не по карточке лида** — после того как первый отчёт по недозвонам
дал 47 «потерянных» вместо 15.

**Мусорные телефоны исключать везде** — по инициативе Тимофея, зашито в представления.

**Рассылку напоминаний не включать до согласования правил** — чтобы первые ложные
срабатывания не убили доверие к системе.

**Разбор звонков откладывался до закрытия организационных дыр** — узкие места оказались
не речевые, а процессные.

  договорённостей (`call_extractions`), а не балльная оценка.
- Крон на сервере целиком принадлежит направлению скоринга заявок. **Ни одна задача по
  звонкам не стоит в кроне** — сбор, расшифровка и разбор работают как постоянные сервисы
  в контейнерах.
- В `.env` присутствуют `YANDEX_METRIKA_TOKEN`, `YANDEX_DIRECT_*` — они относятся
  к смежному направлению, в этом чате не настраивались.
